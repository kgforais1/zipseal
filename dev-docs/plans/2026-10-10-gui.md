# Plan: Desktop GUI

Date: 2026-10-10
Status: in-progress
Linked: TODO.md "Build the desktop GUI"

## Goal

Give people who avoid the terminal a small window that does what
`zipseal -o OUT PATHS…` does. The GUI is a front end only. It must reuse
`collect` and `pipeline.write_archive` and must not fork any archive logic.

## Decisions

- **Toolkit: Tkinter (stdlib).** It adds no dependency, ships with the
  uv-managed Python (Tk 9.0 confirmed), and runs on macOS, Windows and Linux.
  PySide6 looks nicer but adds ~100 MB and a large supply-chain surface to a
  security tool. Revisit only if Tkinter blocks a must-have feature.
- **Entry point:** a second script, `zipseal-gui = "zipseal.gui:main"`, in
  `pyproject.toml`. The CLI stays the primary interface.
- **Shared core:** add a typed `Options` dataclass and a
  `run_job(options, get_password, progress, warn)` function that holds the
  body of `cli.run`. The CLI builds `Options` from argparse. The GUI builds it
  from widgets. `pipeline.py` (`make_layout`, `check_fits`, `estimate_parts`,
  `write_archive`) switches from `Namespace` to `Options`, and the test helpers
  that pass a `Namespace` change with it.
- **`Options` fields:** `paths`, `output`, `max_size`, `level`, `excludes`,
  `default_excludes`, `follow_symlinks`, `hide_names`, `order`, `manifest`,
  `no_verify`, `force` and `dry_run`. Each default matches the CLI default.
- **Password checks live in the core.** `run_job` calls
  `passwords.check_strength` on every password, so the GUI cannot skip the
  empty-password rejection. Its warnings go to the `warn` sink, which the CLI
  points at stderr and the GUI points at the log area.
- **Threading:** run the job in a worker thread. Report progress and
  warnings to the Tk main loop through a `queue.Queue` polled with `after()`.
  Never touch widgets from the worker.
- **Progress:** define `Progress` as a protocol with `part_started`,
  `bytes_written` and `part_verified`. Hook it into `one_part`, the chunk loop
  in `write.py` (`_Members`/`_Tee`), and the verify loop. The CLI's existing
  TTY progress lines become one `Progress` implementation, so there is a
  single mechanism.

## Screen

One window, top to bottom:

1. An input list with "Add files…", "Add folder…" and "Remove" buttons.
   Drag-and-drop is out of scope for v1 because Tk needs a third-party
   extension for it.
2. An output path field with a "Save as…" picker.
3. Options: max part size (preset menu plus custom), compression level,
   hide names, excludes (one glob per line), follow symlinks, and
   "Overwrite existing files" (maps to `force`). If the output exists and the
   box is unticked, ask before running instead of failing.
4. A password section: two masked fields (enter and confirm), or a
   "Generate password" checkbox.
5. "Dry run" and "Create archive" buttons, a progress bar and a log area.

## Security rules for the GUI

These extend `AGENTS.md` and `SPEC.md` §7.

- Password fields are always masked. There is no "show password" toggle in v1.
- Generate the password on the main thread before the worker starts. Pass
  the worker a callback that returns it. Show it in a modal only after the
  archive is written and verified.
- The modal has a "Copy" button and warns that other apps can read the
  clipboard. Clearing is best-effort: clear 60 seconds after copying and when
  the modal closes, before the Tk root is destroyed. Compare with
  `clipboard_get` inside a `TclError` guard and clear only if it still holds
  the password.
- Pass the password through the existing `get_password` callback. Never store
  it on a long-lived object, in settings, or in the log area.
- Clear the password fields after each run, success or failure.
- Do not persist any settings in v1. That avoids writing paths or options to
  disk.
- Error dialogs show `ZipsealError` messages only. Unexpected exceptions show
  a generic message, not a traceback with locals.
